# نقشه‌ی استاندارد مشترک عرضه و تقاضای فضاجو — نسخه ۱

**مبنای بررسی:** `Fazajoo_FOR_CHATGPT(20261101-214446).zip`، snapshot مورخ ۲۰۲۶/۱۱/۰۱.

**وضعیت این مرحله:** پایه فنی آزمایشی / فقط خواندنی / بدون تغییر رفتار محصول. این بسته هیچ migration یا تغییری در فرم‌های زنده، اعلان‌ها، امتیازهای «خبرم کن»، فرصت‌های مشاوران و اطلاعات آگهی انجام نمی‌دهد.

## ۱) تصمیم اصلی

به‌جای کپی‌کردن فرم‌های تقاضا در عرضه، هر دسته **یک واژگان مشترک با دو نقش مستقل** دارد:

- عرضه (`offer`): واقعیت‌های تأییدشده یا اعلام‌شده توسط مالک؛ مثلاً `areaSqm = 18`، `cover = covered`، `access = anytime`.
- تقاضا (`wanted`): شرط‌های مطلوب/حداقل‌ها/حداکثرها؛ مثلاً `minAreaSqm = 12` و `maxRentRial = ...`.
- عمومی: دسته، شهر، مساحت (مترمربع)، مبلغ (ریال)، دوره مبلغ و وضعیت آگهی.
- ویژه هر دسته: کلیدهای پایدار با enumهای مشخص؛ متن آزاد فقط مکمل است و جای شرط قابل‌تطبیق را نمی‌گیرد.

**نام یکسان به معنی مقدار یکسان نیست.** به‌عنوان مثال `minHeightM` در تقاضا با `heightM` در عرضه مقایسه می‌شود. `maxRentRial` سقف بودجه متقاضی است ولی `rentRial` اجاره واقعی اعلام‌شده مالک.

## ۲) اصول حفاظتی

1. مقدار نامعلوم `null` است؛ نه صفر، نه `false` و نه «ناموجود». فیلدی که در آگهی قدیمی پرسیده نشده، حق ندارد مانع قطعی تطبیق شود.
2. رهن و اجاره جداگانه مقایسه می‌شوند؛ اجاره روزانه با ماهانه خودکار مقایسه نمی‌شود؛ مبلغ ریال است و تغییر واحد خودکار نداریم.
3. آگهی قدیمی هرگز به‌صورت ساختگی «کامل» نمی‌شود. تبدیل داده با ثبت منبع (`legacy-fields`، `wanted-metadata`، `legacy-wanted`) انجام می‌شود.
4. تطبیق سه نتیجه دارد: `compatible`، `incompatible`، `needs_details`. «درصد» تا زمان اعتبارسنجی موتور و سیاست امتیازدهی ندارد.
5. فرایند فنی جدید نباید شماره تماس، موقعیت دقیق، اطلاعات حقوقی یا فایل‌های رسانه را وارد نمایه تطبیق کند.
6. تطبیق «مناسب برای پیشنهاد» با «مجوز تماس مشاور» یکی نیست؛ رضایت مالک، اعتبار فرصت، محدودیت حساب و کنترل دسترسی همچنان باید مستقل و سمت سرور اعمال شوند.
7. «خبرم کن»، تطبیق درخواست‌های ثبت‌شده و شبکه مشاوران سه مصرف‌کننده داده مشترک‌اند؛ هرکدام حق انتشار اعلان یا پیشنهاد فقط طبق سیاست اختصاصی خود را دارد.

## ۳) وضعیت کد موجود

- ۹ دسته اصلی وجود دارد: پارکینگ، انبار، سوله/کارگاه، زمین، سایر، مغازه، باغ، ویلا، مسکونی.
- عرضه‌های مسکونی/ویلا/باغ/مغازه از JSONB اختصاصی استفاده می‌کنند؛ دیگر دسته‌های عرضه عمدتاً از فیلدهای عمومی استفاده می‌کنند.
- بسیاری از درخواست‌های تخصصی در ابتدای `description` با تگ‌های نسخه‌دار ذخیره می‌شوند. پاک‌کردن یا بازنویسی کورکورانه آن فیلد خطر از دست رفتن داده دارد.
- امتیازدهی «خبرم کن» در سرویس سمت سرور با دسته، شهر، مساحت، مبلغ و گاهی خواب کار می‌کند؛ موتور تطبیق مشاوران در کد فرانت‌اند مستقل است. نباید هیچ‌کدام بدون تست مقایسه‌ای جایگزین شوند.

## ۴) نقشه فیلدهای عرضه و قواعد UX پیشنهادی

| دسته | حداقل برای شروع سریع | بخش «مشخصات بیشتر» و قواعد شرطی |
|---|---|---|
| پارکینگ | نوع وسیله، مسقف/روباز، مستقل/مزاحم، مساحت | ساعت دسترسی، محدودیت ارتفاع *فقط مسقف*، امنیت، امکانات |
| انبار | نوع فضا، مساحت، دسترسی خودرو | ارتفاع *فقط سرپوشیده*، امکانات بارگیری، شرایط محیطی/امنیت |
| سوله/کارگاه | سوله یا کارگاه، مساحت، برق، ارتفاع | توان برق، نوع کف، بارگیری، جرثقیل *اگر موجود*، امکانات ایمنی |
| زمین | کاربری اعلام‌شده، مساحت، محدوده مکانی | انشعابات، محصوربودن، مسیر دسترسی، آب و شرایط بهره‌برداری؛ کاربری ادعایی را مجوز قطعی تلقی نکنیم |
| سایر | نوع فضا به زبان ساده، کاربری‌های قابل ارائه، مساحت | امکانات، محدودیت‌ها، عکس واقعی و توضیح تکمیلی |
| مغازه | نوع تجاری، مساحت، شرایط اجاره | موقعیت، طبقه، ویترین/بر، رهن، سرقفلی *در صورت انتخاب آن نوع واگذاری* |
| باغ | نوع استفاده، مساحت، آب/برق | امکانات رفاهی فقط در صورت وجود بنا؛ آب و آبیاری در صورت باغداری |
| ویلا | نوع اقامتگاه، ظرفیت، خواب، قیمت دوره‌ای | امکانات، قوانین اقامت؛ سؤال‌های ساحل/جنگل فقط زمانی که واقعاً معنی‌دارند |
| مسکونی | زیرنوع، مساحت، خواب، رهن و اجاره | طبقه/واحد فقط وقتی با زیرنوع ساختمان سازگارند؛ امکانات و تأسیسات |

نکته: این جدول، **طرح پیشنهادی UX** است نه ادعای پیاده‌سازی فعلی. مرحله اول نباید همه این فیلدها را اجباری کند. تکمیل مشخصات اختیاری می‌تواند با یک پیام کوتاه کمک کند («اطلاعات بیشتر = پیشنهاد دقیق‌تر»)، بدون ترساندن کاربر.

## ۵) ساختار ذخیره‌سازی پیشنهادی برای گام بعد

ستون جدید `spaces.space_attributes JSONB NOT NULL DEFAULT '{}'::jsonb`، با نسخه و دسته، برای **عرضه**؛ مثال صرفاً طراحی:

```json
{
  "schemaVersion": 1,
  "category": "parking",
  "values": {
    "vehicleUsage": "both",
    "cover": "covered",
    "access": "anytime",
    "parkingStyle": "independent",
    "entranceHeightCm": 210
  }
}
```

- این ستون هنوز در این بسته **ایجاد نشده** است. هرگز از درج این مثال در پایگاه داده عملیاتی به‌صورت دستی استفاده نکنید.
- بک‌اند باید نام فیلد/نوع/enum/محدوده اعداد/سقف حجم را white-list کند؛ تکیه به اعتبارسنجی فرانت‌اند کافی نیست.
- `description` باید برای متن انسان باقی بماند. تگ‌های تقاضای قدیمی را تا اجرای migration جداگانه دست‌نخورده نگه می‌داریم.
- `PATCH` باید اگر کلید `spaceAttributes` نفرستاده شد، داده قبلی را حفظ کند؛ تبدیل آگهی‌های قدیمی نباید اطلاعات حدسی تولید کند.
- در زمان به‌روزرسانی فیلدهای عرضه، ثبت/ویرایش/جزئیات/پیش‌نمایش و جست‌وجو باید همگی در همان مرحله هماهنگ شوند.
- فیلدهای تخصصی مرتبط با آگهی‌های مشاور باید به API برسند؛ تطبیق صرفاً در فرانت‌اند برای انتشار اعلان کافی نیست.

## ۶) مسیر اجرای کنترل‌شده

**مرحله صفر — همین بسته:** استاندارد JSON، تبدیل‌کننده‌ی فقط‌خواندنی، مقایسه‌کننده سه‌حالته و تست؛ هیچ تغییر رفتاری ندارد.

**مرحله یک — پارکینگ و انبار:** کامپوننت‌های عرضه با سؤال‌های شرطی، ستون JSONB با migration امن و نگهداری داده قدیمی، اعتبارسنجی سمت سرور، ثبت/ویرایش/جزئیات، تست ذخیره و بازیابی، تست مرورگر/موبایل. پس از تأیید کاربر، Commit مستقل.

**مرحله دو — سوله/کارگاه، زمین، سایر:** همان الگو، با فیلدهای کاربردی دسته و کمترین تعداد سؤال اجباری.

**مرحله سه — بازبینی ظریف ۴ دسته دیگر:** رفع تکرار/پرسش نامربوط، بهبود سیاست مبلغ، نمایش ظاهری و پیش‌نمایش.

**مرحله چهار — مقایسه در حالت سایه (`shadow`):** روی داده‌های آزمایشی، خروجی استاندارد جدید با خروجی فعلی «خبرم کن» و مشاوران مقایسه شود. در این مرحله **هیچ نوتیفیکیشن واقعی** توسط موتور جدید ارسال نشود. خطای مثبت/منفی بررسی شود.

**مرحله پنج — فعال‌سازی تدریجی:** طراحی امتیازدهی معتبر، ruleهای category-specific، تست کارایی و کنترل رضایت/اعتبار/محدودیت برای مشاوران، سپس feature flag و تست میدانی.

## ۷) فایل‌های این بسته

- `shared/space-standard.v1.json`: قرارداد واحد دسته‌ها و کلیدهای مشترک/تخصصی (فعلاً پیشنهاد فنی، نه تنظیم زنده).
- `src/utils/spaceProfile.js`: تبدیل فقط‌خواندنی داده آگهی موجود و متادیتای درخواست به نمایه استاندارد.
- `src/utils/spaceCompatibility.js`: بررسی «سازگار / ناسازگار / نیازمند اطلاعات بیشتر» بدون درصد و بدون ارسال اعلان.
- `tests/space-standard.test.mjs`: آزمون‌های مستقل Node؛ بدون دیتابیس، سرویس SMS یا کلید محیطی.

### آزمون در ویندوز

در ریشه پروژه فضاجو، بعد از جایگزینی/افزودن فایل‌ها:

```powershell
node --test tests/space-standard.test.mjs
```

برای این چهار فایل جدید `npm install`، فایل `.env` یا اتصال به سرور لازم نیست. در این بسته هیچ فایلی از فرم‌ها، APIها، DB schema یا موتور فعلی جایگزین نشده است.
