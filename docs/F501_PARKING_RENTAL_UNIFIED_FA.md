# F5-01 — پارکینگ، عرضه و تقاضا، کوتاه‌مدت و بلندمدت

مبنا: آخرین وضعیت تأییدشده شاخه `main` پس از Commit `7d26119` (مرحله F5-00B). این بسته یک موتور تطبیق تازه نمی‌سازد؛ از `shared/rental-term-policy.v1.json` و `shared/rental-term-core.mjs` موجود استفاده می‌کند.

## قرارداد واحد؛ فرم تخصصی

| مورد | عرضه | تقاضا |
|---|---|---|
| کوتاه‌مدت | مبلغ استفاده ساعتی/روزانه/هفتگی + ضمانت خسارت مستقل و اختیاری | سقف بودجه استفاده برای همان دوره + سقف ضمانت خسارت اختیاری |
| بلندمدت | رهن کامل، فقط اجاره یا رهن و اجاره؛ اجاره ماهانه/سالانه | سقف رهن و/یا اجاره؛ اجاره ماهانه/سالانه |
| مشخصات فضا | نوع وسیله، مسقف/روباز، دسترسی، ارتفاع ورودی، امنیت | کاربری، محدوده متراژ اختیاری، نوع پارکینگ، دسترسی و شرایط موردنیاز |
| تغییر قرارداد | پاک‌سازی مبالغ حالت قبلی در فرم، پیش‌نمایش و داده ذخیره‌شده | همان قاعده؛ سقف بودجه هرگز «قیمت مالک» نیست |

**محدودیت مهم ستون قیمت عمومی:** ساختار فعلی `price_type` فقط مقادیر `daily / weekly / monthly / yearly / negotiable` را می‌پذیرد. برای **پارکینگ ساعتی** مبلغ واقعی داخل `spaceAttributes.values` عرضه یا metadata تقاضا نگهداری می‌شود و کارت و صفحه جزئیات از همان اطلاعات تخصصی استفاده می‌کنند. ستون عمومی برای نرخ ساعتی `negotiable` است، بدون اینکه نرخ واقعی را «توافقی» بنامیم. موتور تطبیق عمومی نباید بر اساس قیمت عمومی پارکینگ ساعتی درباره سقف بودجه قضاوت کند؛ اتصال مالی تخصصی به موتورهای عملیاتی، فاز مستقلی با تست جامع خواهد بود.

## مسیرهای اجرایی که این بسته تغییر می‌دهد

- ثبت و ویرایش عرضه/تقاضای پارکینگ: قرارداد در مرحله مشخصات، پیش‌نمایش مالی در مرحله نهایی؛ فیلد عمومی قیمت در این دسته پنهان است.
- ذخیره‌سازی: عرضه داخل `space_attributes` JSONB موجود؛ تقاضا داخل metadata استاندارد `description` موجود؛ بدون مهاجرت پایگاه داده.
- اعتبارسنجی سمت سرور: پالایش مبالغ و شرایط پارکینگ و به‌دست‌آوردن ستون‌های قیمت از قرارداد تخصصی؛ جلوگیری از اشتباه رهن با اجاره.
- نمایش: کارت و صفحه جزئیات، کادرهای جداگانه و واضح برای مدت، دوره، اجاره، رهن، ضمانت و سقف‌های تقاضا؛ اگر متراژ اختیاری وارد نشود، به‌جای آن مقدار ساختگی نمایش داده نمی‌شود.
- هشت دسته دیگر، کدهای تخصصی‌شان و هسته RT-00 دست‌نخورده‌اند. هیچ ماژول موتور تطبیق تازه‌ای ساخته نمی‌شود.

## معیار کنترل دستی پیش از Commit

1. عرضه ساعتی، روزانه و هفتگی: ثبت و ویرایش، نمایش قیمت دقیق در کارت و جزئیات، بدون برچسب اشتباه «توافقی» برای ساعتی.
2. عرضه ماهانه و سالانه، هر سه قرارداد رهن کامل/اجاره/رهن‌واجاره: تأیید مبالغ جداگانه؛ عدم درج رهن در ستون اجاره.
3. تقاضای ساعتی با متراژ اختیاری خالی و با محدوده: کارت و جزئیات در هر دو حالت، سقف بودجه و ضمانت.
4. تقاضای بلندمدت: رفتن به مرحله بعد، بازگشت، عوض‌کردن «رهن و اجاره» به «فقط اجاره»، بررسی پاک‌شدن مبلغ رهن در پیش‌نمایش، ذخیره، کارت و جزئیات.
5. نبود انتخاب مدت، نبود روش مالی، نرخ نامعتبر: پیام خطای مرتبط در خود بخش مالی.
6. صحت ثبت/ویرایش آگهی باغ، ویلا، مسکونی و سایر فضاها، به‌عنوان آزمون رگرسیون مرورگر.
7. پس از `node --test tests/*.test.mjs` و `npm run build`، در GitHub Desktop فقط فایل‌های این مرحله و هیچ فایل محرمانه‌ای دیده شود.

**وضعیت فنی این بسته:** ۵۲۲ آزمون Node موفق در محیط آزمایشی و بررسی parse JSX با TypeScript. Build Vite به علت نبودن بعضی بسته‌های npm در محیط آزمایش اجرا نشده و باید روی رایانه کاربر اجرا شود. آزمون end-to-end واقعی با مرورگر و سرور محلی نیز باید انجام شود؛ از قبل «تأییدشده» اعلام نمی‌شود.

## آماده‌سازی چهار دسته بعدی

برای انبار، سوله/کارگاه، مغازه و زمین **همین هسته قرارداد** به‌کار می‌رود، ولی دوره‌ها، مبلغ‌ها و شرایط مطابق سیاست همان دسته انتخاب می‌شوند. کوتاه‌مدت انبار الزاماً ساعتی نیست؛ برای سوله پروژه‌ای و زمین فصلی باید قرارداد/کاربری مستقل بررسی شود؛ سرقفلی مغازه و مزارعه زمین به اجاره عادی تبدیل نمی‌شود. قراردادهای خاص بدون تأیید شرایط لازم وارد تطبیق خودکار نمی‌شوند.

## داده‌های آزمایشی

طبق تصمیم صاحب پروژه، آگهی‌های فعلی آزمایشی‌اند و قبل انتشار حذف می‌شوند. بنابراین این بسته **هیچ تبدیل داده قدیمی یا اسکریپت migration** ندارد. اگر آگهی قدیمی بدون ساختار جدید را در ویرایش باز کنی، فرم جدید از او می‌خواهد قرارداد معتبر جدید انتخاب شود.
